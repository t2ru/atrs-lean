# 型の棚卸し

[ADR bf1b](../decision/bf1b-make-illegal-states-unrepresentable.md) は、値の妥当性の条件を型に置くことを求める（規則は [lang/lean/rules.md](../lang/lean/rules.md#不正な状態を表現できない型)）。
検査 MISU-1（`scripts/ci/check_lean.py`）が見つけるのは、包むだけの `structure` と型の外の述語だけである。条件付きの欄、並行する写し、位置の組は見つけない。
そこで、型を足すたびに、次の観点で棚卸しする。

## いつ行うか

- 機能を取り込み、`Spec`・モデルに型を足すとき
- 移植元・移植先の版上げの後（[upgrade.md](upgrade.md)）
- 登録簿・道具の誤りが「作れてはいけない値」から生じたとき

## 観点

| 観点 | 兆候 | 型での表し方 |
| --- | --- | --- |
| T1 条件付きの欄 | 「〜のときだけ」「〜なら必須」と書いた欄、別の欄の値で意味が変わる欄 | 和型。構築子ごとに要る欄だけを持たせる |
| T2 空でない・長さ | 「1 つ以上」「1〜6 件」「長さ 1 か 2」 | 証明フィールド付きの `structure`。決まった形なら和型（`oneWay f \| roundTrip o h`） |
| T3 範囲・形式 | 「0〜23」「数字 10 文字」「`D-NNN` の形」 | 証明フィールド（既定 `by decide`）と、検証の関数 `ofX? : Raw → Option X` |
| T4 旗と `Option` の組 | `Bool` と `Option` が一緒に決まる、一緒に立つ `Bool` | 1 つの和型 |
| T5 位置の組 | `A × B × C` の成分の意味を docstring で決めている | 名前付きの `structure` |
| T6 並行する写し | 同じ値を 2 か所に持ち、等しいことを docstring で求める | 片方を消し、導く関数にする |
| T7 文字列のコード | 有限の綴り（コード・層・種類）を `String` で持つ | 列挙と `toCode` |
| T8 並行する列 | 2 つの列が同じ長さであることを求める | 組の列にする |
| T9 境界 | 外部から来る値（入力・環境・DB の行） | 生の型（`@[raw_input "<理由>"]`）のまま置き、検証の関数で検証済みの型に移す |

## 手順

1. **範囲を決める。** 足した型だけか、層全体か。
2. **観点ごとに洗い出す。** 範囲が広いときは、層ごとに別のエージェントに分けてよい。その場合も結果は候補であり、各候補を Lean の位置で裏付ける。
3. **候補を分ける。**
   - 述語のまま残すもの（機械の PRE・INV、独立な入力の間の関係、環境の全体にわたる性質。ADR bf1b の規則 3）。理由を記録して閉じる。
   - 型に移すもの。生成器・α・証明への影響を見積もる。
   - `Spec` の振る舞いが変わるもの（型にすると、いまの仕様では作れる値が作れなくなる。例: 上限の無い採番と固定長の書式）。作業を止め、選択肢を示して判断を求める（[workflow.md](workflow.md#判断を記録する事項)）。
4. **移す。** 型を変え、作る側（字面・生成器・α・テストの読み取り）を直す。字面には、既定 `by decide` の証明とマクロを使う。
5. **ギャップを見直す。** 抽象側の PRE の成分が型に移ったら、その成分を `excludedBy` に挙げた項目を付け替える。具体側に抽象側の型で表せない値ができたら、前提型の差異（具体側の入力・状態）に入れる（[gap-inventory.md](gap-inventory.md)）。
6. **記録する。** 範囲・各件の判断・残したものの理由を、プロジェクトの意思決定記録に残す。
