# 差異の棚卸し

差異の登録簿（`@[gap_entry]`。[lang/lean/trace-attributes.md](../lang/lean/trace-attributes.md#ギャップの登録簿)）は、機能を取り込むたびに項目を足して育つ。
検査（TR-D・TR-K・GK）は、登録簿と Lean の宣言の形の対応を確かめるが、次のことは確かめない。

- `Spec` の事前条件（PRE）の成分のそれぞれが、どれかの差異か PRE の外の項目に結びついていること
- 登録簿の説明・前提の文が、いまの Lean の宣言と原典を正しく述べていること
- 未着手の機能について、原典と仕様文書のあいだの違いが漏れなく登録されていること
- 未着手の R 課題について、登録簿の R 課題（`rTasks`）と課題表の差異の列が一致していること

そこで、ときどき全範囲を棚卸しする。棚卸しは、移植の手順（[process.md](process.md)）の外にある点検の作業である。

## いつ行うか

- 実装済みの機能が増えて、次の大きな機能に着手する前
- 移植元・移植先の版上げの後（[upgrade.md](upgrade.md)）
- 登録簿・課題表の誤りが 1 件見つかったとき（同じ経路の誤りが他にもありうる）

## 手順

1. **範囲を決める。** 実装済みの機能だけか、未着手の機能も含めるか。未着手を含めると、原典を読む量が大きく増える。原典は版を固定した手元の写し（submodule など）を読む。
2. **観点ごとに突き合わせる**（下の表）。範囲が広いときは、観点ごとに別のエージェントに分けてよい。その場合も、結果は候補であり、一致の根拠にしない（[SKILL.md](../../../SKILL.md#原則) の原則 A）。各候補を、原典の位置・Lean の位置・仕様文書の位置で裏付ける。
3. **候補を分ける。**
   - 判断を要しないもの: 誤記、古くなった名前・欄、欠けた箇所の印 `@[gap]`、文書の引用の不足、検査の取りこぼし。そのまま直す。
   - 判断を要するもの: 差異の追加・拡大、PRE の強化、`Spec` の変更。作業を止め、一件ずつ選択肢（差異として登録する／`Spec` を原典に合わせる／見送る）と影響を示して判断を求める（[workflow.md](workflow.md#判断を記録する事項)）。
   - 確かめられないもの: ライブラリ・処理系の内部の挙動に拠る候補。原典実行（[spec/conformance.md](../spec/conformance.md)、言語パックの `harness.md`）で採取してから判断する作業項目に回す。
4. **反映する。** 判断に従って登録簿・印・課題表・仕様文書を直し、生成表を再生成する（`trace manifest`）。未着手の機能の前提型の差異は、述語が無いので `deviations := []` と `.pending … (some W)` にし、W 課題を課題表に足す。
5. **記録する。** 範囲・方法・各件の判断・保留を、プロジェクトの意思決定記録に残す。保留は作業項目にする。

## 観点

| # | 観点 | 見るもの | よくある取りこぼし |
| --- | --- | --- | --- |
| G1 | PRE の成分の結びつき | 各 R 課題の `Spec` の PRE・環境の前提の連言のそれぞれについて、PRE の外での具体側の振る舞いを確かめ、どれかの項目（PRE の外・前提型）があるか | 誤った不変条件の名前を注記した成分（実際にはその不変条件に含まれない条件）。引数の値域の条件 |
| G2 | 証拠の宣言 | `excludedBy` が PRE の述語を指しているか（定数でなく）。`refuted` の定理・`pending` の W 課題が実在するか | 値域の定数だけを指す証拠 |
| G3 | 箇所の印 | 差異の生じる `Spec`・具体側の定義（`Assert`・例外・上書き・折り返しの箇所）に `@[gap]` があるか。属性の列の中の `gap` も数える | 例外を投げる共通の部品、状態の表の型、設定の型 |
| G4 | 述語と欄 | `@[deviation]` と `deviations` の対応、前提の文が述語の実際の定義と一致するか（欄の名前・条件の強さ）、種類（抽象側／具体側の入力・状態・環境）が述語の引数と合うか | 述語を改めた後に残った古い欄の名前 |
| G5 | R 課題 | 登録簿の `rTasks` と課題表の差異の列が両向きに一致するか。差異を引き継ぐ複合の R 課題（画面・API など）に挙がっているか | 番号の打ち間違い、引き継ぎの漏れ |
| G6 | 箇所の参照 | `sites` の文書とアンカーが実在し、差異の起きる節を指しているか | アンカーの無い参照、節の改名 |
| G7 | 文書の引用 | 仕様文書の「[Source] は…」「原典の不具合」などの記述が、差異の ID を引用しているか。引用した ID の内容と記述が合うか | 表の中の段落、引用の無い既知の振る舞い |
| G8 | 原典との突き合わせ（未着手の機能） | フォームと検証の注釈、フレームワークの暗黙の処理（前後の空白の除去・データバインダ・メッセージの解決・JSON の型の変換）、トランザクションの境界、件数の検査、列の型と変換の型、整列、例外から応答への写し | 検証と登録が別のトランザクション、リストの自動の伸長、列の型の幅、Unicode の空白 |
| G9 | 観測の形 | 原典実行の採取に、仕様に無い欄・形が出ていないか | getter が JSON の欄として出るもの |
