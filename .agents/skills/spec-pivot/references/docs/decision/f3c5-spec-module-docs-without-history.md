# Spec のモジュール文書には仕様だけを書き、根拠は章の末尾の「根拠と対応」節にまとめる

## Context and Problem Statement

仕様の散文は `Spec` のモジュール文書に書き、本にする（[ADR c634](c634-spec-prose-in-lean-module-docs-and-book.md)）。
形式化を段に分けて進めると、モジュール文書に「第 2 段で置く」「作業項目 xxxx で足す」のような作業の経緯がたまる。形式化を終えた後も「形式化前の草案」の表示が残る。本を読む人（移植先を実装する人、仕様を確かめる人）にとって、これらは何が正しいかを読み取る妨げになる。
一方、根拠の意思決定記録や既知差異、対応するモデルへのリンクは、仕様を確かめる人に要る。
適用先 ATRS のオーナーは、ドキュメンテーションコメントを仕様書として分かりやすくするよう求めた（来歴: ATRS の ADR b385）。

## Decision Drivers

* 本の地の文を、通して読める仕様書にすること
* 根拠と、他の層への対応を辿れること
* 道具が読む字面（`出典:` の行、区分）を保つこと

## Considered Options

* 本文に仕様だけを書き、根拠と対応を章の末尾の節にまとめる
* 経緯も根拠も本文から除く（意思決定記録から辿る）
* 区分の表示の誤りだけを直し、経緯は残す

## Decision Outcome

Chosen option: "本文に仕様だけを書き、根拠と対応を章の末尾の節にまとめる", because 本文が仕様だけになり、根拠と他の層への対応は 1 か所にまとまって辿れるため。すべて除くと、仕様を確かめる人が根拠を探す手間が増える。経緯を残すと、形式化が進むたびに本文が古くなる。

規則は [spec-documents.md](../rules/spec-documents.md#モジュール文書に書く) に置いた。

* 前文と本文に、作業項目の ID・段・経緯の物語を書かない。意思決定記録への参照は、意味の説明に要るときだけ短く書く。
* 各章の末尾に `## 根拠と対応` を置き、根拠の意思決定記録、関係する既知差異、対応する移植元モデルのモジュール、抽象化の証明のモジュール、適合テストベクタの場所を挙げる。
* 序のモジュール（`Spec` の入口）に、区分と記号の凡例と、章の表を置く。
* 区分の表示は実態に合わせる。形式化済みの章に「形式化した時点で置き換える」の決まり文句を書かない。
* 証明のための補題・SPEC 課題の定理は、章の中の「性質」の見出しの下にまとめ、業務の節と見分けられるようにする。

### Consequences

* Good, because 本の地の文が仕様だけになり、形式化が進んでも古くなる記述が減る。
* Bad, because 経緯は本から辿れなくなる。経緯は意思決定記録・作業項目と git の履歴で辿る。
