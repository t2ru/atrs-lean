# 作業の進め方（既定）

人と AI エージェントが、この方法で移植を進めるときの **既定の進め方** を示す。
手順そのもの（何を作り、何が通れば次へ進むか）は [process.md](process.md) が定める。本書は、その周りの進め方を扱う。どこから手を付けるか、どこで判断を記録するか、完了をどう判定し、作業をどう記録するか。

**本書の位置づけ。** 本書の項目は、選んで使える既定（任意）である。段階の分け方・判断の体制・ゲートの組み方・記録の形式は、プロジェクトが自分の規約で置き換えてよく、一部だけを使ってもよい。
置き換えても、次は変わらない。
- [SKILL.md](../SKILL.md#成立の条件) の成立の条件と、[process.md](process.md#完了の定義機能ごと) の完了の定義
- 「[判断を記録する事項](#判断を記録する事項)」の表。既存の規則の再掲である。置き換えてよいのは、誰がいつ判断するかである

置き換えた内容を、プロジェクトの規約に書いておくとよい。

## 評価

形式化に入る前に、適用する範囲を決める。結果は、移植するかどうか、どこまで適用するかの判断の材料になる。

- 対象（機能・モジュール）ごとに、適用の前提 P1〜P6（[SKILL.md](../SKILL.md#適用の前提参考)）を満たすかを表にする。満たさない前提には、理由と代わりの扱い（範囲から外す、規範節にする、限界に載せる）を書く。
- 形式化する範囲と、範囲外・保証の限界に残すものを分ける。
- 規模とリスクの材料を集める。例:
  - 観測可能な振る舞いの数
  - 不足している言語パックと `LangSemantics` の演算
  - オラクル化できない構成
  - 見込まれる差異
- 評価はここで終えてもよい。終了点の例を次に示す。

| 終了点 | 得られるもの |
| --- | --- |
| 評価だけ | 前提の充足表、適用範囲の案、規模とリスクの材料 |
| 一部の機能 | 選んだ機能について、完了の定義を満たした移植 |
| 全体 | 適用範囲のすべての機能について、完了の定義を満たした移植 |

## 判断を記録する事項

次の事項は、証明でも検査でも決まらない。そのため、どの体制でも、プロジェクトの意思決定として理由とともに記録する（[process.md](process.md#原則)、[verification.md](verification.md#保証の限界)、[traceability.md](traceability.md#対象外)）。

| 事項 | 機械で決まらない理由 |
| --- | --- |
| `Spec` の意図（標準の選択、事前条件、不変条件が業務どおりか） | リファインメントは `Spec` の妥当性を保証しない |
| 差異・非決定性の扱い（再現するか、`Spec` で正すか、前提・成分・環境の前提の広さ） | 意図の判断を伴う。広すぎる成分や強すぎる前提は、不具合を吸収しうる |
| 範囲からの除外（機能・対象・入力の範囲） | 除外は、黙った機能の欠落になりうる |
| 外部から見える約束の変更（入出力の形式・プロトコル） | 利用者に影響する |
| 信頼の基盤の採用（検証器・生成器・処理系とその版） | 証明の外にある |
| 保証の限界を受け入れるか | 何を保証しないかは、利用者が決める |

### 既定の体制

- 判断するのは人とし、AI はこれらに当たった時点で作業を止め、選択肢とそれぞれの影響を示して判断を求める。
- 止まる条件は、AI のその場の判断ではなく、事前に決めた条件で判定するとよい。例:
  - 差異・非決定性・範囲外の登録簿に行を足す、または既存の行を広げる
  - 事前条件を強める
  - 差異の述語・環境の前提・標準の抽象化の核（`@[deviation]`・`@[nondet]`・`@[env_pre]`・`@[kernel]`）を足す・広げる
  - `Spec` の標準の選択を変える
- それ以外の作業（モデル・証明・ベクタ・生成物を作る作業）は、検査が通る限り AI が進めてよい。証明の正しさは Lean の核が、形と追跡は検査器が確かめる。ただし、上の表の事項に当たる変更は、作業の途中で生じても止まる対象である。
- 判断者、止まる条件の増減、判断の頻度（都度か、区切りごとか）は、プロジェクトが決めてよい。

## 検査ゲート

- 完了は、できる限り検査の実行結果で判定する。自己申告（「実装した」「確認した」）では判定しない。
- process.md の「次へ進む条件」と完了の定義の各項目のうち、機械で確かめられるものには検査を対応させる。それらを 1 つの入口から実行できるようにしておくと、人も AI も同じ判定を再現できる。機械で確かめられない項目（例: 原典の振る舞いを洗い出したこと）は、人の確認であることを明示しておく。
- 検査器そのものが効いていることを確かめるとよい。例:
  - わざと違反する入力（反例・違反例）を置き、検査器が失敗を返すことを確かめる。
  - 検査器を一時的に壊すと、失敗になることを確かめる。

  違反例で確かめていない迂回は、検査器の限界である。保証の限界の文書の検査器の行に関わる。
- 段階導入（警告から始める検査）は、[traceability.md](traceability.md#検査) の規則に従う。

## 未着手の可視化

- コード単位の網羅は、インベントリと追跡の検査 TR-S1 が確かめる（[traceability.md](traceability.md#検査)）。
- コード単位に現れない振る舞い（フレームワークの暗黙の処理、設定、メッセージなど）は、手順 1 の「観測可能な振る舞いの一覧」で管理するとよい。各行に処理状況を付ける。例: 形式化済み・差異として登録・規範節に記述・限界に記載・範囲外（理由）・未着手。機能の完了時に未着手が残っていないことを確かめるとよい。
- 仮の実装を残さない工夫をするとよい。Lean の `sorry` は検査で禁じている。移植先の言語にある仮実装の構文（例: Rust の `todo!`・`unimplemented!`）が業務機能に残っていないことも、検査で確かめられる。

## 独立した敵対的レビュー

設計の段階と完了を宣言する前に、作業とは別の文脈（別のエージェントや別の人）による敵対的レビューを行うとよい。

- レビュー側には、作業側の推論を渡さない。渡すのは、一次資料（原典、モデル、証明、登録簿、限界の文書）と、レビューしてほしい宣言や設計だけにする。
- 観点の例:
  - 空虚化の抜け道（義務と検査をすべて満たしたまま、自明に成り立つ例を作れるか）
  - 未登録の差異
  - 広すぎる差異の述語・成分
  - 範囲の黙った縮小
  - 限界の文書の漏れ
  - 原典の振る舞いの見落とし
- レビューの結果は、一致の根拠に数えない（原則 A。[verification.md](verification.md#決定論的な手段)）。指摘は、できる限り次のどれかに落とし、同じ誤りが機械で再び検出されるようにする。
  - 反例
  - 違反例を置いた検査
  - 限界の文書の行
  - 差異の登録
- 指摘と対応を、意思決定記録などに残しておくとよい。
- 誰が、何回、どの範囲でレビューするかは、プロジェクトが決める。

## 画面の確認（Web アプリ）

画面の応答を照合するベクタ（例: HTTP レベルの要求と応答）は、状態・遷移先・データを照合する。ただし、画面の構造や、ブラウザでの操作の流れは照合しないことが多い。

- その部分の補助として、ブラウザで操作の流れを再現するテストを使える。
- このテストは、両端の一致の根拠に数えない。期待値がモデルから生成したものでないためである（[verification.md](verification.md#適合テストベクタの運用)）。移植元の出力を期待値にして移植先に通すと、移植元と移植先を直接つなぐことになる。
- 両端の一致の根拠にしたい振る舞いは、モデルに入れ、ベクタとして生成する。
- ベクタで照合しない画面の部分は、保証の限界の文書に載せる。

## 記録と中断への備え

AI エージェントの作業は、文脈の上限やセッションの終了で途切れる。次のものをリポジトリ内に残しておけば、別の担当者や新しいセッションが作業を引き継げる。

| 記録 | 内容 |
| --- | --- |
| 作業状態 | いま何をしていて、次に何をするか。未完の項目と、止まっている判断 |
| 意思決定記録 | 判断を記録する事項の判断と、その理由 |
| 学んだこと | 言語・フレームワークの落とし穴。言語パックの `frameworks.md`・`semantics.md`、または本スキルに還元する |

- 作業の区切りごとに、検査が通る状態で版管理に記録するとよい。
- 記録の形式と置き場所は、プロジェクトが決める（例: 作業項目の一覧、意思決定記録のディレクトリ、作業ログ）。
