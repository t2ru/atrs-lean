# 作業の進め方（既定）

人と AI エージェントが、この方法で移植を進めるときの **既定の進め方** を示す。
手順そのもの（何を作り、何が通れば次へ進むか）は [process.md](process.md) が定める。本書は、その周りの進め方を扱う。どこから手を付けるか、どこで人が判断するか、完了をどう判定し、どう記録するか。

**本書の位置づけ。** 本書の内容は、すべて推奨である。次の 2 つを満たす限り、段階の分け方・判断点・ゲートの組み方・記録の形式は、プロジェクトが自分の規約で置き換えてよい。
- [SKILL.md](../SKILL.md#移植が成り立つ条件) の成立の条件
- [process.md](process.md#完了の定義機能ごと) の完了の定義

置き換えたときは、何をどう置き換えたかをプロジェクトの規約に書く。一部だけを使ってもよい。

## 評価

形式化に入る前に、適用する範囲を決める。結果は、移植するかどうか、どこまで適用するかの判断の材料になる。

- 境界・機能ごとに、適用の前提 P1〜P6（[SKILL.md](../SKILL.md#適用の前提)）を満たすかを表にする。満たさない前提には、理由と代わりの扱い（範囲から外す、規範節にする、限界に載せる）を書く。
- 形式化する範囲と、保証の限界に残す範囲を分ける。
- 規模とリスクの材料を集める。例:
  - 観測可能な振る舞いの数
  - 不足している言語パックと `LangSemantics` の演算
  - オラクル化できない構成
  - 見込まれる差異
- 評価はここで終えてもよい。終了点の例を次に示す。

| 終了点 | 得られるもの |
| --- | --- |
| 評価だけ | 前提の充足表、適用範囲の案、規模とリスクの材料 |
| 一部の機能 | 選んだ機能について、完了の定義を満たした移植 |
| 全体 | 適用範囲のすべての機能について、完了の定義を満たした移植 |

## 人が判断する事項

証明と検査は、モデル・証明・ベクタ・生成物の正しさを機械で確かめる。そのため、それらを作る作業は、検査が通る限り AI が自律して進めてよい。
人の判断が必要なのは、証明と検査では決まらない次の事項である。

| 事項 | 理由 |
| --- | --- |
| `Spec` の意図（標準の選択、事前条件、不変条件が業務どおりか） | リファインメントは `Spec` の妥当性を保証しない |
| 差異の扱い（再現するか、`Spec` で正すか、差異の前提・成分の広さ） | 意図の判断を伴う。広すぎる成分は、不具合を吸収しうる |
| 範囲からの除外（機能・境界・入力の範囲） | 除外は、黙った機能の欠落になりうる |
| 外部から見える約束の変更（入出力の形式・プロトコル） | 利用者に影響する |
| 信頼の基盤の採用（検証器・生成器・処理系とその版） | 証明の外にある |
| 保証の限界を受け入れるか | 何を保証しないかは、利用者が決める |

- 既定では、AI はこれらに当たった時点で作業を止める。そのうえで、選択肢とそれぞれの影響を示して、判断を求める。判断と理由は意思決定記録に残す。
- 止まる条件は、AI の判断ではなく、事前に決めた条件で判定するとよい。例:
  - 差異の登録簿に行を足そうとしている
  - 範囲外の一覧に項目を足そうとしている
  - `Spec` の標準の選択を変えようとしている
- 止まる条件の増減、まとめて判断する頻度（都度か、区切りごとか）は、プロジェクトが決めてよい。

## 検査ゲート

- 完了は、検査の実行結果で判定する。文章の承認や自己申告では判定しない。
- process.md の「次へ進む条件」と完了の定義の各項目に、それを確かめる検査を対応させる。それらを 1 つの入口から実行できるようにしておくと、人も AI も同じ判定を再現できる。
- 検査器そのものが効いていることを確かめる。例:
  - わざと違反する入力（反例・違反例）を置き、検査器が失敗を返すことを確かめる。
  - 検査器を一時的に壊すと、失敗になることを確かめる。

  見逃しのある検査器は、通っても根拠にならない。
- 段階導入（警告から始める検査）は [traceability.md](traceability.md#検査) の規則に従う。

## 未着手の可視化

- コード単位の網羅は、インベントリと追跡の検査 TR-S1 が確かめる（[traceability.md](traceability.md#検査)）。
- コード単位に現れない振る舞い（フレームワークの暗黙の処理、設定、メッセージなど）は、手順 1 の「観測可能な振る舞いの一覧」で管理するとよい。各行に処理状況を付ける。状況は、形式化済み・差異として登録・範囲外（理由）・未着手のどれかとする。機能の完了時には、未着手を無くす。
- 仮の実装を残さない。Lean の `sorry` は検査で禁じている。移植先の言語にある仮実装の構文（例: Rust の `todo!`・`unimplemented!`）が業務機能に残っていないことも、検査で確かめるとよい。

## 独立した敵対的レビュー

設計の段階と完了を宣言する前に、作業とは別の文脈（別のエージェントや別の人）による敵対的レビューを行うことを推奨する。

- レビュー側には、作業側の推論を渡さない。渡すのは、一次資料（原典、モデル、証明、登録簿、限界の文書）と、レビューしてほしい宣言や設計だけにする。
- 観点の例:
  - 空虚化の抜け道（義務と検査をすべて満たしたまま、自明に成り立つ例を作れるか）
  - 未登録の差異
  - 広すぎる差異の述語・成分
  - 範囲の黙った縮小
  - 限界の文書の漏れ
  - 原典の振る舞いの見落とし
- レビューの結果は、一致の根拠に数えない（原則 A。[verification.md](verification.md#決定論的な手段)）。指摘は、できる限り次のどれかに落とし、同じ誤りが機械で再び検出されるようにする。
  - 反例
  - 違反例を置いた検査
  - 限界の文書の行
  - 差異の登録
- 指摘と対応は、意思決定記録などに残す。
- 誰が、何回、どの範囲でレビューするかは、プロジェクトが決めてよい。

## 画面の確認

HTTP レベルのベクタは、応答の状態・遷移先・データを照合する。ただし、画面の構造や、ブラウザでの操作の流れは照合しないことが多い。その部分の補助として、ブラウザで操作の流れを再現するテストを、移植元と移植先の両方に通す手段がある（任意）。

- 固定した入力・時計・データで決定論的に実行するなら、適合テストベクタと同じく決定論的な手段に数えてよい。その場合、確かめた範囲（操作の流れ・画面）を、限界の文書に書く。
- 期待値は、移植先ソースの出力から作らない（[verification.md](verification.md#適合テストベクタの運用)）。

## 記録と中断への備え

AI エージェントの作業は、文脈の上限やセッションの終了で途切れる。次のものをリポジトリ内に残しておけば、別の担当者や新しいセッションが作業を引き継げる。

| 記録 | 内容 |
| --- | --- |
| 作業状態 | いま何をしていて、次に何をするか。未完の項目と、止まっている判断 |
| 意思決定記録 | 人が判断した事項とその理由。差異・除外・限界の受け入れを含む |
| 学んだこと | 言語・フレームワークの落とし穴。言語パックの `frameworks.md`・`semantics.md`、または本スキルに還元する |

- 作業の区切りごとに、検査が通る状態で版管理に記録するとよい。
- 記録の形式と置き場所は、プロジェクトが決める（例: 作業項目の一覧、意思決定記録のディレクトリ、作業ログ）。
