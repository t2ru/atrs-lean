# SQL: 検証

## 移植元として

原典の SQL を `LangSemantics.Sql` の式として 1 文ずつ写す。`Abstraction` で、`SourceModel` のリポジトリ（写した照会と更新）が `Spec` のポートの操作をリファインすることを証明する。
一致の前提（整列キーの単射性、マスタの不変条件など）は、リファインメント定理の PRE・INV か、名前付きの差異の仮定として明示する。

SQL の写しは手による翻訳なので、原典の SQL との一致を次の決定論的な手段で確認する。

| 手段 | 何を確かめるか | 保証の限界 |
| --- | --- | --- |
| 処理系の差分実行: 同じデータベースの状態とパラメータについて、原典の SQL を実際の処理系（方言パックの `harness.md` で版と設定を固定）で実行した結果と、写した式を `LangSemantics.Sql` で評価した結果を照合する。順序が未規定の照会は、処理系の結果が「許される結果の集合」に含まれることを照合する | 1 文ずつの写しが一致する | 照合したデータとパラメータの外は保証しない。照合したデータの選び方（境界・NULL・同順位を含むこと）を限界の文書に書く |
| 方言の意味論の突き合わせ: `LangSemantics.Sql.<Dialect>` の演算（型変換・書式・整列）を、処理系の実行結果と突き合わせる | 方言の写しが一致する | 突き合わせた値の範囲 |

- 並行実行での振る舞い（分離レベル・ロック）は写さない。各文・各トランザクションは原子的に扱う。実際の並行実行との一致は保証の限界である。

## 移植先として

- 移植先が SQL を使う場合、移植先の SQL も `LangSemantics.Sql` の式として `TargetModel.Repository.*` に写し、`Refinement` で `Spec` との一致を証明する。
- 実行する SQL と `TargetModel` の写しの一致は、移植元と同じ「処理系の差分実行」と、`target-model/` のベクタで確認する。対応は追跡注釈（[locators.md](locators.md)）で示す。
- 移植元と移植先で DBMS が異なる場合は、両方の方言（`LangSemantics.Sql.<Dbms>`）で写す。方言の差（採番・型変換・照合順序）で `Spec` と一致しなくなる点は、移植先の既知差異 `T-NNN`（前提型または観測型）として登録する。その差異には、`@[deviation]`・R 課題・W 課題を置く。無名の前提にしてはならない。
- 並行実行の性質（直列化可能性）は Lean では扱わない。モデルでは各操作を原子的に扱う。実装の並行実行がどれかの逐次実行と一致することは、次の 2 つで確認する。
  - 分離レベルの指定（例: SERIALIZABLE と再試行）
  - 固定した実行順の結合テスト（決定論的）

  確認しきれない実行順は、保証の限界の文書に書く。設計レビューは補助にとどめ、一致の根拠にしない。
