# 検証の使い分け

## 決定論的な手段

両端（ソース ⇔ モデル）の一致は、**決定論的な検証または変換** で確認しなければならない。
決定論的とは、機械が実行し、同じ入力に対して常に同じ判定を返すことをいう。

| 手段 | 種類 | 何を保証するか | 典型的な限界 |
| --- | --- | --- | --- |
| Lean の証明 | 検証 | 全入力についてのモデル間の関係（`Abstraction`、`Refinement`、`Spec` の不変条件） | 公理と Lean の核を信頼する |
| 決定論的な生成 | 変換 | 生成物が生成元と同じ意味を持つこと（例: `TargetModel` → Verus の写し） | 生成器と対応表を信頼する |
| 移植先の検証器 | 検証 | ソースと生成した写しが、全入力で一致すること（例: Verus） | 検証器が扱えるコードの範囲。検証器の意味論を信頼する |
| 有界モデル検査 | 検証 | 有界な入力で、パニック・未定義動作が無いこと（例: Kani） | 境界の外 |
| 適合テストベクタ | 検証 | モデルとソースの振る舞いが、固定した入力で一致すること | ベクタの入力の外 |
| 移植元オラクル | 検証 | 原典そのものを実行した結果と、`SourceModel` の一致。版上げ時は新旧 2 版の差分 | 実行した入力の外。ハーネス化できない部分 |
| 処理系の差分実行 | 検証 | 手で写した言語の断片（例: SQL）について、実際の処理系の結果と `LangSemantics` の評価結果が一致すること | 実行したデータの外。写しの網羅 |
| 有限域の全探索・固定シードの性質テスト | 検証 | 列挙した範囲・生成した入力での一致 | その範囲の外 |
| 追跡の検査 | 検証 | 網羅性・陳腐化・直接接続の禁止・差異の対応（[traceability.md](traceability.md)） | 対応の意味までは確かめない（意味は上の手段で確かめる） |

- 人や LLM の判断は、一致の根拠にしてはならない。補助にとどめる。例: レビュー、設計レビュー、敵対的レビュー、目視の確認、判断に基づくハッシュの更新。
  - レビューの指摘は、できる限り反例・違反例を置いた検査・限界の文書の行に落とす（[workflow.md](workflow.md#独立した敵対的レビュー)）。
- 言語ごとに使える手段と、その限界は、言語パックの `verification.md` に役割（移植元／移植先）ごとに書く。
- 証明が未完の性質を、性質テストで代用してはならない。未完は作業項目に残す。

## 保証の限界

決定論的な手段が届かない部分は、プロジェクトの **保証の限界の文書** に、境界ごとにすべて列挙する。列挙する項目は次のとおり。
- 境界（例: 移植元ソース ⇔ `SourceModel`）
- 対象（機能・モジュール）
- 使っている手段
- 保証しないこと
- 信頼している基盤（検証器・生成器・処理系）

- 限界を新しく作ったら（例: ハーネスの対象外、Kani の境界、ベクタに無い入力の範囲）、同じ変更で文書に追記する。
- モデル間（Lean の証明）にも、証明の届かない部分がある。次を必ず載せる（[architecture.md](architecture.md#空虚化を防ぐ義務)）。
  - 仕様の妥当性（`Spec` の標準の選択が業務の意図どおりか）
  - 名前付きの成分（差異の述語・観測の成分・非決定性）の広さ（必要性は証明で確かめるが、広さは変異テストの兆候と人の判断による）
  - 複合の R 課題での差異の冗長な使用（必要性は少なくとも 1 つの R 課題についてだけ示す）
  - 環境の非決定性による活性
  - 「中断」の差異の前提を破った後の軌跡
- 移植先の検証器で、証明を省く・仮定する構文（Verus の `assume` / `admit` / `external_body` / `assume_specification` / `external_fn_specification` など）を、業務機能と証明で使ってはならない。検証の外に置く境界（Verus の `#[verifier::external]` など）は、言語パックが定める種類に限り、その一覧を限界の文書に載せる。上の構文をやむを得ず使う場合は、次の 3 つを満たす。
  - 意思決定として記録する。
  - 場所と理由を限界の文書に列挙する。
  - 具体化の課題一覧からリンクする。

## 信頼の連鎖

```
移植元ソース ─(オラクル・差分実行: source-model/ ベクタ)→ SourceModel ─(Lean 証明)→ Spec ←(Lean 証明)─ TargetModel ─(生成)→ 写し ─(移植先の検証器)→ 移植先ソース
                                                                                                    └─(target-model/ ベクタ・有界検査)→ 移植先ソース
```

- 内側の 2 本は、リファインメントの証明である（[architecture.md](architecture.md#リファインメントb-メソッド)）。
- 両端は、決定論的な手段で確認する。証明が届く範囲（例: 生成した写しと検証器）と、テストで確かめる範囲を区別し、後者の範囲を限界の文書に書く。
- 移植先言語でモデルを写したもの（例: Verus の spec 関数）は、`TargetModel` から **生成** する。手で書いたり直したりしてはならない。CI で再生成し、差分が無いことを確認する。

## 適合テストベクタの運用

- 形式は [conformance.md](conformance.md)。
- 期待値の出所:

| ディレクトリ | 出所（`source`） |
| --- | --- |
| `spec/`, `shared/` | Lean `Spec` の実行（`lean-spec`。標準の選択 `run`） |
| `source-model/` | Lean `SourceModel` の実行（`lean-source-model`）と移植元オラクル（例: `java-oracle`） |
| `target-model/` | Lean `TargetModel` の実行（`lean-target-model`） |

- 手計算の例は、Lean 側のテストとして置く。生成値と手計算が食い違ったら、どちらが誤りかを調べてから直す。
- 生成したベクタはコミットする。モデルの変更でベクタが変わったら、その差分を確認する。差分の確認は補助であり、正しさの根拠は、生成元のモデルの証明とオラクルの照合である。
- 移植先ソースの出力からベクタを作ってはならない。
- 「今日」はベクタに明示する。実行時の日付に依存するベクタを作ってはならない。
- 移植元オラクルの値と `SourceModel` の値が一致しなければ、`SourceModel` 側の不具合とみなす。

## 証明の運用

- 未完の定理を `sorry` で残してはならない。未完のものは作業項目に残し、定理自体をコミットしない。
- 新規の `axiom` を追加してはならない。CI で `#print axioms` を確認する。
- `native_decide` と `bv_decide` は `Lean.ofReduceBool` の公理を持ち込む。そのため、`Abstraction`・`Refinement`・`Spec` の定理と、それらが依存する定義・補題で使ってはならない。有限な具体値の確認は `decide` で行う。`native_decide`・`bv_decide` を使ってよいのは `Tests` だけである。
- `Spec` 自身の義務（標準の選択が関係に含まれること、INIT ⇒ INV、INV の保存）も、証明課題として管理する。
- リファインメントの主定理（R 課題）は、`Machine.Refines` の形でなければならない。主定理の仮定は、PRE・INV・`@[deviation]` 付きの述語だけとする。ポートの契約は、モデルのポート実装についての R 課題で証明する。
