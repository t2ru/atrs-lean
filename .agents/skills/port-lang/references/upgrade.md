# 版上げへの追従

`SourceModel` は追従中の **最新版 1 つ** だけを表す。旧版は VCS のタグ（例 `upstream-<release>`）で参照する。
1 回の版上げを 1 つの作業単位とし、プロジェクトの意思決定記録に残す。

## 移植元の版上げ

### 1. 意思決定記録を作る

旧 release・新 release・上げる理由を書く。完了時に採択する。

### 2. 移植元を上げる

- 移植元ソースを（例: submodule として）新しい commit に上げる。
- `trace/upstream.json` を更新する。対象は release、commit、依存の版、言語・処理系の版。依存の抽出方法は言語パックの `frameworks.md` に従う。

### 3. インベントリ差分を取る

`inventory source` で新しいインベントリを作り、`diff` で旧版と比べる（例: `diff --old git:<旧版のコミット>`。宣言の版の新旧も比べる）。ロケータごとに次のどれかに分類される。

| 分類 | 判定 |
| --- | --- |
| 不変 | 本文ハッシュが同じ |
| 本文変更 | 同じロケータで本文ハッシュが違う |
| 移動/改名 | 旧ロケータが消え、同じ本文ハッシュの新ロケータが現れた |
| 追加 / 削除 | 上記以外で、新版にだけ / 旧版にだけある |
| 版の変化 | `dep`・`lang` の版文字列が違う |

ハッシュで判別できない改名は `trace/renames.json` に `{ "old": "<ロケータ>", "new": "<ロケータ>" }` として手で書く。この対応は、`rehash` が新しいロケータについて決定論的な検査を実行し、合格したときに限って受け入れられる（[traceability.md](traceability.md#検査済みハッシュ)）。

### 4. 差分オラクルを実行する

`source-model/` の全ベクタ入力を、旧版と新版の移植元ソースで実行して出力を比べる（実行方法は言語パックの `harness.md`）。
出力が変わったケースは「振る舞いの変化」である。コード差分の有無にかかわらず、手順 6 の判断対象になる。依存フレームワークの挙動の変化は、コード差分には現れず、ここで初めて見つかることが多い。

### 5. 影響一覧を生成する

`impact` で影響一覧を作る。起点は、手順 3 で変化したロケータ（`impact --diff git:<旧版のコミット>`）と、手順 4 で出力が変わったケースの `modelDef` である。次の順に伝播させる。

1. `@[source]` に変化したロケータを含む `SourceModel`・移植元 `LangSemantics` の定義
2. それを使う `Abstraction` の定理
3. その定理に現れる `Spec` の定義
4. その `Spec` を使う `Refinement` の定理と `TargetModel` の定義（`Spec` を変える場合だけ）

### 6. 層ごとに判断する

| 状況 | 対応 |
| --- | --- |
| 本文変更・版の変化はあるが、差分オラクルに変化が無く、`SourceModel` の定義も変わらない | `rehash` で、その定義にかかる決定論的な検査（オラクル・差分実行）を実行し、合格すれば道具がハッシュだけを更新する。ベクタの入力の外の変化は検出できないので、その定義を覆うベクタが十分かを見直す（[traceability.md](traceability.md#検査済みハッシュ)） |
| 移植元の振る舞いが変化した | `SourceModel` を直し、`Abstraction` を再証明する。続けて次のどちらかを選ぶ |
| └ `Spec` が追従する（業務の意図が変わった） | 意思決定を記録して `Spec` を変える。`Refinement` → `TargetModel` → 移植先ソースの順に直す（写しはハッシュずれで自動的に要再検査になる） |
| └ `Spec` は維持する | 既知差異 `D-NNN` を追加し、`Abstraction` のリファインメント定理に名前付きの仮定（または成分）を加え、差異の証拠を証明する |
| 追加 | 通常の手順（[process.md](process.md)）で扱う。対象外とするなら、移植の範囲外とする意思決定を記録し、それを `out-of-scope.json` に書く |
| 削除 | `SourceModel` から外す。`Spec` に残すかを意思決定として記録する |
| 移動/改名 | `@[source]` のロケータを書き換える（ハッシュは同じ） |

`Spec` は業務の意図が変わるときだけ変える。移植元の挙動変化をそのまま `Spec` に流してはならない。

### 7. ベクタを再生成する

- `source-model/` を新版のオラクルで再生成する（`upstream` キーを新版にする）。
- `Spec` を変えた場合は、`spec/` と `target-model/` を Lean から再生成し、移植先の写しも再生成する。
- 差分を確認する（補助。正しさの根拠は、モデルの証明とオラクルの照合）。

### 8. 完了する

1. 追跡の検査・全証明・全検証を通す。差分オラクルの対象外とした入力など、新しい限界を保証の限界の文書に追記する。
2. 意思決定を採択し、変更履歴に記録する。
3. 旧版の最後のコミットにタグ `upstream-<旧 release>` を付けてから、版上げをコミットする。

## 移植先の版上げ

ツールチェーン・検証器・依存の版上げも同じ流れで扱う。

1. `trace/target.json` を更新する。
2. `dep`・`lang` の版が変わった `@[target]` を持つ `TargetModel`・移植先 `LangSemantics` の定義について、`rehash` で決定論的な検査を実行する。
3. 写しを再生成し、移植先の検証器（言語パックの `verification.md`）を再実行し、`target-model/` のベクタを通す。

各言語パックの `frameworks.md` に、その言語で起こりがちな挙動変化の例を載せる。
